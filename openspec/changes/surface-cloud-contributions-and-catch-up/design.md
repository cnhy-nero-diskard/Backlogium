## Context

See proposal.md — Why. The current reader keeps a durable read position and bounded audit rows, but its last reconstructed snapshot is in memory. Settings' Read now consumes one page; placement drains pending pages only when a Steam delta has a sufficiently long observation gap. Cloud ingest writes shared-game sessions through the on-device presence mechanism, and owned-game placement replaces actions produced by Steam playtime diffing. Neither `Session` nor `PlaySession` stores contribution provenance. History expands day → game → session, while Diagnostics already shows a raw cloud/local comparison.

The reader's position is shared by Settings, placement, ingest, and historical re-file. `readCompleteHistory` resets/drains it, and `readRemainingHistory` holds a sequence mutex across pages; a new background path must join that sequencing rather than race it. The separate Settings-information-architecture change moves the cloud controls under Data & privacy. The normative reader requirement that an unconfigured app presents no cloud-derived state still applies.

## Goals / Non-Goals

**Goals:**

- Make a session's cloud contribution a durable fact, not an inference from configuration, game source, or timestamps; qualify mixed contributions.
- Let a configured phone eventually consume the poller's observations even when ordinary Steam sync does not ask for placement, while keeping routine volume deliberately small.
- Keep History oriented toward play, with a short route to the evidence and the limits of that evidence.

**Non-Goals:**

- Change the cloud poller's one-minute cadence, Firestore access rules, or raw observation schema.
- Add a server-side session detector, derived values, a complete local mirror of cloud transitions, or precise wall-clock background execution.
- Guarantee the entire Firebase project remains inside a free allowance: other functions, reads, writes, storage, and traffic share its budget.

## Decisions

### 1. Record contribution at the same write boundary as the session

Extend the session ledger with nullable, structured per-session contribution evidence, independent of `GameSource` and `RecomputeSource`. Store two independent facts: recovered shared-game play and cloud-informed timing of Steam-owned minutes. Each fact has its own `UNKNOWN`, `NONE`, `FULL`, or `PARTIAL` state, so one row can carry both facts and partiality applies to the specific fact rather than to a single mutually exclusive kind. New session writes start with `NONE` for both facts; the migration leaves legacy rows `UNKNOWN`. The domain repository projects both facts for History; product UI does not read a Room entity. Legacy rows remain unknown, including sessions created before provenance existed, even where their timestamps resemble cloud intervals.

Shared-game ingest marks the recovery fact only when accepted cloud evidence actually credits time. Owned-game placement marks the timing fact only when the replacement actions materially differ from the unaided actions; an unchanged or rejected suggestion does not earn a mark. An extension of a pre-existing unmarked open session makes the newly added cloud fact partial, as does an extension that adds unmarked local play to a session with an existing cloud fact. Updating one fact never clears the other. Store enough contribution metadata to keep both facts truthful on future extension, source conversion, re-file, rollback, and merge; do not equate a single enum kind or boolean `cloud=true` with every minute in the session having been observed. Persist provenance atomically with the credited session and its baseline/progress write, and do not make a cloud read itself write a label.

A historical re-file marks each replacement session whose timing actually changes as cloud-timed, while preserving any recovered-play fact and any prior timing evidence. The timing fact is full only when the whole replacement session is timed by the accepted interval evidence, and partial when only a portion is; a no-op or rejected interval adds no fact. Save the exact prior two-fact provenance with the original rows so reversal restores it byte-for-byte.

*Alternative rejected:* deduce provenance from whether a game is family-shared or a cloud interval overlaps a session. Both create false positives, and a missed/failed read becomes indistinguishable from an actually used one.

### 2. Treat routine catch-up as a third acquisition trigger, not a new derivation path

Extend the existing repository's account-bound, serialized read/consume path with a bounded multi-page catch-up. Reuse the ingest callback and shared read cursor; hold the read-sequence lock across a bounded attempt and advance the cursor only after each page's effects are consumed. Before advancing a routine page, persist its owned-game intervals, including their coverage metadata, in a small, account-bound pending-placement evidence store. Upsert by Steam account, app id, and interval start so page overlap refines an interval rather than duplicating it. This is acquired timing evidence only: a routine read does not write a session, place Steam minutes, or create session provenance. If a routine read runs before Steam reports the matching increase, a later accuracy-driven placement combines pending intervals intersecting its diff window with any still-unread intervals before applying the existing complete-window and coverage rules; it must not judge completeness from the suffix alone. Keep the evidence until the Steam sync commits the corresponding baseline/actions, removing consumed evidence in that same commit so a failed or interrupted placement can retry it. Account changes and reader removal clear account-bound pending evidence. Report complete only at `hasMore=false`. A cap of four pages per attempt bounds one job even if the 31-day initial window is unusually dense; another eligible attempt resumes from the saved position. A failed page preserves already-consumed pages and their pending evidence, and reports partial/failure rather than falsely clearing the backlog. Keep the historical re-file's complete-history drain and placement's time-window proof unchanged. A routine catch-up alone must not retrospectively attribute owned-game minutes: the existing placement path and deliberate historical sweep retain that authority.

Pending-evidence retention applies to every operation that advances the shared reader position, not only routine catch-up: successful verification (including endpoint replacement), manual Read now, accuracy-driven placement reads, and the complete-history drain used by historical re-file must all persist owned-game intervals before saving the next position. Keep these pages in the existing serialized sequence. Consume their effects through a durable, idempotent page protocol: if ingest or evidence persistence fails, do not advance that page's position; if effects commit but saving the position fails, replay safely upserts the same evidence and the ingest watermark prevents duplicate credit. If a later Steam baseline/session commit fails, pending evidence remains available for retry. No cursor-advancing path may silently discard owned-game intervals.

An interval emitted as ongoing at a terminal read is provisional, not a final row. Retain its opening transition or equivalent current-state boundary alongside the pending interval. A later page containing only the closing transition uses that retained boundary to reconstruct and upsert the same `(account, reader generation, app id, start)` interval with its final end and coverage; it must not leave the old ongoing version or lose the close. For successive Steam deltas, intersect the retained interval with each app's diff window. On a committed per-app Steam baseline, prune closed intervals only when their end is at or before the new baseline; retain an interval that extends beyond that baseline so a later delta can use its later portion. Apply the same pruning after a successful no-delta baseline advance, which otherwise strands evidence that can never intersect a future diff window.

Evidence is retired by the committed per-app baseline, not by the first delta that overlaps an interval: a commit may use only its own diff-window intersection, and an interval whose end is later than the new baseline remains stored in full (with its original boundary) for a later delta. A closed interval is removed only once its end is at or before the committed baseline, including a no-delta commit.

Persist a monotonically increasing reader generation with the configured reader and bind pending evidence and fetched pages to both Steam account and that generation. A successfully verified endpoint replacement starts a new generation, deletes prior-generation pending evidence, and fences responses/work captured under the old generation before they can persist evidence or move the cursor. Reader removal and account change also advance/fence the generation and delete pending evidence; `AccountRoomReset` performs the account-change deletion in its Room transaction. Evidence from a prior generation is never combined with a replacement reader's history.

*Alternative rejected:* let routine pages call only the shared-game ingest callback. That callback discards owned-game intervals, so advancing the shared cursor before Steam reports the matching increase leaves placement with a suffix it must reject.

*Alternative rejected:* call `read()` once per day. One page is not necessarily the end, and a read that advances the shared cursor before the client consumes it can permanently skip shared-game observations.

### 3. One minimum-gap admission gate for the new routine triggers

Initialize Automatic only when a reader is first successfully verified and no routine policy has been persisted. A successful verification that replaces an already configured reader for the same Steam account preserves the selected policy and last admitted routine attempt; it does not reset the shared cooldown. Automatic offers one periodic opportunity daily plus a play-end opportunity, with a 12-hour minimum gap across both. Overrides set a shared minimum gap of 12, 24, or 48 hours and a corresponding periodic opportunity; play-end can run sooner than the next periodic opportunity only when its gate has elapsed. Persist the selected policy and last admitted routine attempt (including a failed attempt, recorded when work actually begins rather than when it is merely queued offline) so process death, reboot, duplicate events, and network retries cannot produce an automatic request burst. Use unique WorkManager work with network constraints; an already-running routine job absorbs another routine request. Give routine admissions and successful reads by other paths persisted monotonic ordering watermarks, seeded by reader verification, rather than comparing read age to a chosen time window. The latest successful manual or placement read may satisfy one pending routine opportunity only if it reached `hasMore=false` and its completion watermark is newer than the latest admitted routine attempt; consume that watermark when it satisfies the opportunity. An older terminal read and a latest partial read do not suppress catch-up. Do not throttle manual reads or accuracy-driven placement. Only a configured, account-matching reader can admit work. After successful replacement verification, fence/cancel old-endpoint work and schedule against the replacement under the preserved policy and cooldown; on removal or account change, fence in-flight reads and clear/cancel scheduled work as appropriate. Preference handling follows the configured reader, not the cloud service's poll schedule.

Reconcile this policy at startup/upgrade as well as on a new verification event. If an already configured, previously verified reader has no persisted routine policy, initialize Automatic once, seed the initial verification-order watermark from this reconciliation, and schedule its next eligible opportunity under the same gate without requiring the user to verify again. Preserve its existing read and ingest positions and any already persisted policy/cooldown during reconciliation.

Add an explicit Off / Manual only persisted policy rather than using a missing policy as the disabled state: absence still means an older verified reader needs Automatic initialization. Switching Off cancels queued periodic and play-end work and prevents new admissions; an already admitted job stops at a safe page boundary so committed ingest, pending evidence, and cursor position are retained. Do not remove the reader or gate manual Read now and accuracy-driven placement. Preserve the last admitted attempt and ordering watermarks while Off. Re-enabling a cadence schedules future opportunities against that cooldown without an immediate burst; replacement verification for the same account preserves Off just as it preserves any other selected policy. In Settings, put the concise explanation of Automatic and Off adjacent to their controls; place the exceptions (poller cadence, manual and accuracy-driven reads, WorkManager timing) in secondary explanatory text rather than making every option label carry the whole policy.

Recording *attempt* rather than success for the minimum gap is deliberate: an unreachable endpoint must not be hammered by every play-end event. WorkManager's periodic wake-up is an opportunity, not a promised execution time. The schedule is intentionally coarse; measured project usage, page count, and function cost should be checked before raising the offered frequency. This gate caps additional routine starts, not all cloud HTTP calls or the number of pages in one bounded catch-up.

*Alternatives rejected:* an unbounded free-form minute selector (invites excessive reads); applying the gate to correctness-driven placement (can advance a Steam baseline before cloud timing can be used); a separate cloud-side scheduler for phone downloads (cannot force an offline or sleeping phone to ingest).

### 4. Derive a quiet History entry from locally visible contributed sessions

Use the existing day → game → session expansion. The per-session cloud mark is secondary to time and minutes, text-explained through an accessible, sufficiently large action separate from the expansion control. Summarize proven recovery/timing facts only for the currently loaded History window; a session may carry both and appear in both labeled contribution groups, so group counts are fact counts rather than disjoint session counts. Hidden games are already filtered at the session repository boundary. Show the compact Cloud activity entry whenever the reader is configured, including when History has no days or the loaded window has no cloud contributions; keep it absent after reader removal. Label the detail with the loaded window's date range, not an implied all-time log. When there are no contributions, lead with a short empty-state explanation and the reader/observation status rather than two empty fact headings. Otherwise lead with the existing two labeled groups — recovered play and cloud-timed Steam play — and localized singular/plural counts, followed by status and known coverage limitations. Keep progress centered and Back reachable while the detail loads, and verify narrow screens, large fonts, and screen readers. Preserve History's approximate start-time wording; do not imply a timeline-derived duration or a date change when only boundary timing changed. The raw interval-by-interval diagnostic stays in Diagnostics.

Resolve a contribution card against its day key after expanding the day and game; compute its scroll index from the actual keyed lazy-list structure rather than an estimate that omits a Today/earlier section row. Once the target session is composed, bring that specific row into view and confirm the reveal visually/accessibly before consuming the request. If data changes or the loaded window no longer contains the target, present a clear fallback in History instead of silently clearing the request. Test with Today expanded, preceding earlier days expanded, and a target far enough down the list to be initially uncomposed.

*Alternative rejected:* mark a whole day, game, achievement, or quest because cloud was available. A result can combine cloud-assisted and unaided sessions, and the higher-level badge would overstate the evidence.

### 5. Persist a small read summary, not the timeline, for offline status

Keep the existing bounded read audit and persist enough latest accepted read metadata (time, observation watermark where provided, coverage/partial status, trigger/outcome) to show the last attempt and last success after restart. Read success and observation freshness are separate fields; neither proves that the poller's next minute succeeded. The detail must handle no snapshot after restart, a stale latest observation, a failed read after prior success, incomplete history, and an endpoint not configured. Refresh the displayed staleness classification as time passes or the app resumes, without triggering a cloud request solely to update the warning. Do not invent coverage percentages from transition counts or present a missing observation as no play. Reader endpoint/token remain out of History and backup.

*Alternative rejected:* store only the current in-memory `snapshot`. It disappears on process death and makes an offline detail screen appear empty despite existing contributed sessions.

### 6. Version backup provenance without changing session identity

Treat the currently shipped backup as format version 1 and introduce version 2 for session contribution provenance. New exports always write version 2; import accepts exactly versions 1 and 2 and rejects any other explicit version before merge. Apply the same version-aware decode to picked files and retained automatic snapshots. Version 1 is the legacy format with no `cloudContribution` field; a v1 file carrying that v2-only field is rejected as mixed-version input. Because the existing `Json` configuration leaves `encodeDefaults` false and v1's `formatVersion` defaults to 1, a shipped v1 export may also omit the root `formatVersion`; a missing version is therefore read as v1 only when no v2-only provenance field is present. A v2 export must explicitly write `formatVersion: 2` rather than relying on a default that the serializer may omit.

Every session in a v2 file carries a required, non-null `cloudContribution` object with both independent facts: `{"recoveredSharedPlay":"UNKNOWN","timingInformedSteamPlay":"UNKNOWN"}` for legacy-unknown provenance, or a state of `NONE`, `FULL`, or `PARTIAL` for each fact. Both fields are required; `UNKNOWN` is not interchangeable with `NONE`, and the two facts may both be `FULL`/`PARTIAL` on one session. No field may rely on default-value omission. JSON `null` and an absent object or member are invalid in v2. This keeps legacy unknown, known absence, and each independent contribution state distinct under the app's existing JSON settings. Decode the root version before the session payload and retain that distinction through merge; do not change global `Json` flags to make this field work.

For a v1 session with no provenance, insert it as unknown but leave an overlapping local session's known provenance unchanged. For a v2 session, replace both matching contribution facts with the explicit imported values, including clearing a known local fact when the corresponding imported state is `UNKNOWN`; inserts take the same explicit values. Keep natural-key matching and recompute semantics otherwise intact. Credentials/endpoint/watermark and pending interval evidence remain device-local. Re-file reversal must restore both prior facts alongside prior attribution, and removing the reader hides cloud-specific UI without deleting existing recorded minutes or inventing new session origins.

*Alternative rejected:* reconstruct provenance after restore by replaying cloud history. The old evidence may be unavailable, account or coverage may differ, and guessing would make the badge less reliable than an unknown label.

## Risks / Trade-offs

- **[Mixed open sessions accidentally claim full recovery]** → Model partial contributions at the writer boundary; test local-then-cloud and cloud-then-local extensions and reversals.
- **[A session can carry both recovery and timing evidence]** → Store and back up independent contribution facts, render both without treating their groups as mutually exclusive, and test source conversion/restore paths that retain an open row.
- **[Routine catch-up advances the cursor before Steam reports an owned-game increase]** → Persist owned-game intervals before each page advances, combine them with later placement evidence, and remove them only with the corresponding successful Steam commit; serialize the bounded drain using the existing sequence mutex.
- **[A non-routine reader path or terminal page loses pending timing evidence]** → Apply the same effect-before-position retry protocol to verification, manual reads, placement, and re-file; retain an interval boundary to refine an ongoing interval when a later page closes it.
- **[Pending evidence outlives its reader or its Steam diff window]** → Fence evidence by account and reader generation, clear it on replacement/removal/account reset, and prune closed intervals when a committed Steam baseline makes them ineligible for any future diff, including a no-delta baseline.
- **[A routine cooldown still allows costly placement/manual traffic]** → Settings states the scope of the cap; keep its values conservative and verify real read/page usage against the project's budget rather than claiming the schedule guarantees free usage.
- **[A connected player cannot opt out of routine traffic]** → Persist a distinct Off policy, cancel pending work, stop in-flight work safely, and preserve manual and correctness-driven reads plus the existing admission history for later re-enablement.
- **[Status is hidden when there is no attributed play]** → Base the History entry on configured reader status, show an honest empty state for the loaded window, and retain offline reader/observation diagnostics there.
- **[A server outage strands a long backlog]** → Keep per-page position durable, bound attempt work, show partial state, and retry only on another eligible opportunity or manual action.
- **[Older sessions have unknown provenance]** → Never infer it, even when a visible session likely benefited historically; only future writes and explicit reversible re-file can supply evidence.
- **[Two in-flight Settings changes collide]** → Land the Settings-information-architecture change first or rebase this change against it; add the cadence controls once under Data & privacy and keep shared view state/actions.

## Migration Plan

Add nullable, independent session-contribution facts in v37 that leave historical rows unknown. Add the pending interval/boundary Room store in a separate v37-to-v38 migration rather than changing the already-exported v37 schema in place; extend the deep-history migration chain through v38 while retaining the dedicated v36-to-v37 check. Then version backup serialization/import to preserve both facts. Integrate writes at the current shared session/placement boundaries before turning on the UI mark. Schedule routine work only for a verified configured reader, initializing Automatic on first successful verification when no policy exists and reconciling existing verified readers at startup/upgrade. A successful endpoint replacement preserves the selected policy and last admitted routine attempt but starts a new evidence generation, clears old-generation pending evidence, fences old-endpoint work, and schedules against the newly verified reader under the unchanged cooldown; changing the policy replaces its periodic request without resetting the cloud read cursor or ingest position. Reader removal and `AccountRoomReset` delete pending evidence in its Room transaction. A rollback can stop new routine scheduling and hide the History marks while keeping session minutes, the durable read position, and old backups intact. Verify on-device: restore an older backup, recover shared play, place owned play, apply and undo a cloud-informed re-file, interrupt a multi-page drain, and show History offline.
