## Context

See `proposal.md` — Why. Ordinary `readPresence` requests without `position` start at `now - 31 days`; `CloudPresenceRepository.readCompleteHistory()` clears the shared position but still starts there, with a 50-page ceiling. Verification, routine catch-up, accuracy-driven reads, and re-file currently share that position and a sequence mutex. The historical use case keeps originals and created-row IDs for reversal, but recovery recomputes expected rows from caller-supplied intervals. The poller retains transitions indefinitely and writes them only on state changes, not on every minute of unchanged play. First Steam sync creates no sessions for its baseline; the separate opt-in `PlaytimeBackfillUseCase` freezes `max(0, playtimeForever - trackedMinutes)` per owned game in `Game.backfillMinutes`. History reads sessions, whereas the game detail shows session minutes as tracked and this frozen balance as imported. There is no reliably persisted first-baseline timestamp on existing installs; old diagnostic sync runs are pruned.

## Goals / Non-Goals

**Goals:** explicit local-date choice and player-confirmed pre-data cutoff; available lower bound; complete-only, restart-safe, cost-bounded acquisition of an arbitrary retained range; dated pre-data sessions bounded by already-imported Steam minutes and confirmed cloud coverage; stable one-time apply/undo with unchanged combined minutes/XP; preserve all ordinary reader and ingest semantics.

**Non-goals:** a server-side bulk export, an automatic long-running backfill worker, changing retention or the meaning of coverage, changing the poller's cadence, synthesizing Steam-owned minutes from presence alone, or claiming that the poller recovers every pre-install minute.

## Decisions

### Opt-in, fixed-window reads on the same endpoint

Keep ordinary `GET readPresence[?position=...]` exactly as it is. Add `mode=range` as an authenticated metadata lookup returning `earliestObservedAt` (nullable), the current-state evidence where available, and server `readAt`, without transitions; query `presence` ordered by `t` ascending with `limit(1)`, plus the current player document. The earliest retained **transition** is the defensible lower bound when there is a log; if there is no transition but a usable current `since`/`lastObservedAt`, report that retained current-state beginning with its limited coverage rather than pretending an earlier transition exists. A truly empty record returns null. The UI labels this *earliest retained evidence*, not a promise that every intervening minute was observed. Metadata is requested on entering the configured range control/refresh, not appended to every normal page.

An explicit historical page uses `from=<ISO instant>&through=<ISO instant>` and optional `position=<ISO instant>`; `from` and `through` are required together and only for historical reads. Parse strict full UTC instants, reject invalid combinations, `from > through`, future `through`, or a position outside `[from, through]` with 400 before any Firestore read. Authentication and account configuration checks remain first. Query `t >= from` for page one, then `t > position` for later pages, always with `t <= through`, ascending by `t`, `limit(251)`; return at most 250 transitions, `hasMore`, the last timestamp and a truthful page window. The reader uses the existing unique ISO-timestamp document IDs and per-page overlap reconstruction; it does not reinterpret the raw `prev*` fields. Existing normal reads remain recent by default and subsequent normal reads keep their existing cursor. Do not use a server-side multi-page drain: each authorized request has a constant cost bound.

Refresh metadata at confirmation and capture its server `readAt` as `through`, retaining it across retries (the server clock, not a potentially fast phone clock, defines the present). Also retain the account-bound current-state snapshot observed at confirmation, only if its observation is at/before `through`; a later `current` document may have moved past the fixed cutoff and must not be used to infer an interval within it. Reconstruct a terminal current-only interval only from this frozen evidence when it is valid, or report that the last interval cannot be closed from the bounded record. Preserve `windowStart` as the chosen effective instant and `windowEnd` as the actual evidence end (never claim the entire range was observed). At a cut boundary, reconstruct from one bounded predecessor transition (`t < from`, descending, limit 1) **only for the opted-in history**, then clip eligible timing to `[from, through]`; this avoids losing an interval already open at local midnight without allowing the re-file to move minutes to an earlier unselected date. The first-page boundary query adds at most one document/read query. A synthetic boundary must never claim pre-start coverage; preserve the original closing coverage fields and reject uncertain spans through the existing placement rule.

*Rejected:* enlarging default first reads to all history (unbounded on a metered service and violates the spec); encoding an ancient `position` without an explicit mode (a cursor is a strict-exclusive continuation, hides user intent and the available lower bound); returning the oldest observation in **every** ordinary response (another paid query for every routine read); a server-side bulk drain (unbounded execution/read cost). The dedicated metadata mode and explicit time bounds make historical work intentional and visible.

### A separate, durable historical checkpoint and bounded manual batches

Persist a historical operation keyed by Steam account, reader generation, normalized endpoint identity and the confirmed `[from, through]`, together with its frozen current boundary, progress, last complete-page position and last opening transition. Keep its historical intervals/evidence in a dedicated Room staging table, separate from `CloudPendingEvidence` (which Steam sync prunes). Add the corresponding Room migration and account-reset cleanup. Stage one page's reconstructed intervals/overlap boundary and advance its historical position in one Room transaction; replay/upsert by identity and interval start, replacing an ongoing interval with its closed form when the closing transition arrives. If per-page shared-game ingest or owned-game pending-evidence retention fails, do not commit the historical position. If those effects succeed but the Room checkpoint fails, replay is idempotent; existing ingest watermark rules and pending-evidence upsert prevent double-credit. If older shared-game observations fall behind the existing ingest watermark, do not rewind that watermark or promise to regenerate them as part of owned-game re-filing.

**Do not reset or advance the ordinary `cloudReadPosition` for this operation.** Hold `cloudReadSequenceMutex` for each page's capture/fetch/persist (outer to `cloudStateMutex`), not across a whole months-long job. Between pages and between batches, routine, verification promotion, Read now and placement may run; none can steal a historical page because historical progress is independent. Account-change invalidation also fences late fetches; before every page and every commit compare account generation, current Steam ID, reader generation and stored endpoint/credential against captured identity. On endpoint removal, replacement, account change or `AccountRoomReset`, invalidate and delete staged history; a new reader requires a fresh lookup/confirmation. A page already committed to pending evidence remains under its existing identity fence. Verification may fetch outside the locks but its promotion takes the sequence mutex; a stale historical response is discarded before staging. Shared-game ingest still follows the same lock/order and idempotent watermark semantics. Do not let the metadata lookup mutate ordinary positions or establish a successful routine read watermark.

One explicit tap performs **at most 50 pages** (and a UI-scoped time budget, e.g. 30 seconds, checked between pages); each page can return 250 transitions plus one lookahead. At the cap or time budget, preserve the separate checkpoint, show pages/transitions/last covered time and offer **Continue**. Do not loop via WorkManager, auto-retry, or mark a partial re-file applied. Cancel leaves staged progress available until the user explicitly discards it; endpoint/account fences discard it automatically. A response with no further transitions through the frozen cutoff marks acquisition complete, after which application may begin. Progress counts distinguish fetched pages from actual observed coverage.

**Cost envelope:** `maxInstances: 1` and concurrency `1` stay unchanged; invalid authentication reads zero documents. One metadata lookup reads at most one player document plus one oldest-transition query result. A historical page reads at most one player document plus 251 transition query results; the first page can add one predecessor-result query (at most 254 billed documents/query minimums depending on Firestore billing). Thus a 50-page user-confirmed batch is bounded by 50 HTTP calls and roughly 12,650 document reads (plus at most one predecessor lookup); elapsed-time early stop reduces it. A 12-month theoretical worst case **at one transition per poll minute** is 525,600 transitions, about 2,111 pages with one-transition overlap, roughly 43 manual batches and about 535,000 document reads, not 50 pages. The longest selectable interval is from the reported earliest retained evidence to the captured present, so its overall cost grows with the finite number of transitions in that fixed interval; it has **no defensible permanent constant whole-range cap** under indefinite retention. Every incremental spend is bounded and requires a user decision. Display the potential multi-batch nature before confirmation; do not claim a duration-only upper bound because transitions and future retention can grow. If a fixed lifetime budget is required, that would contradict the promise that the earliest retained date always remains selectable and should be a separate product decision.

*Rejected:* increasing `MAX_REFILE_PAGES` to an arbitrary large number (can block other readers, large in-memory accumulation and still fails at some history length); refusing the whole operation after 50 pages (earliest retained would be selectable but not usable); persisting all intervals in DataStore or re-fetching from the beginning per tap (size and billing grow without bound); applying each partial batch to the session ledger (breaks one-time exact reversal and the complete-window rule).

### Calendar choice, eligibility, and the applied receipt

Settings offers a radio/default choice **Recent 31 days (current behavior)** and a calendar-date choice. The untouched default resolves to the same rolling `confirmation instant - 31 days` as the old first read; never silently round it to midnight. A custom date resolves to local midnight in the device's current timezone using `java.time`; custom dates must be strictly before today, on/after the local date of earliest retained evidence, and no later than today's date. For a valid earliest-date choice, the effective start is `max(local midnight, earliest retained instant)`; show both the chosen calendar date and the actual clipped timestamp (with timezone) before confirmation. Refresh the bound and clock at confirmation, rejecting stale/empty or invalid choices; compare UTC instants on the wire, not date strings. On timezone changes, the confirmed instant/range does not shift.

The fixed end is captured at confirmation (the present then, not an endlessly moving now). During application only closed Steam-owned sessions whose recorded span intersects `[effective start, through]` are candidates for **existing-session re-dating**; placement uses only confirmed portions of staged intervals inside that window and leaves a session unchanged unless all its minutes can be safely placed **within** the chosen range. No prior date is rewritten and no split can be dated before the chosen start. Retain the original overlap/coverage metadata for safety. The app reports both *requested calendar range* and *actually evidenced range*, because these can differ during poller outages. Availability is a bound, not proof of continuous coverage. For the untouched default, preserve existing session-selection behavior at the rolling 31-day boundary except for the explicit no-outside-range guarantee.

Keep the completed staging and frozen operation descriptor until `CloudPresencePlaytimeRefilingUseCase.apply` durably sets its applied marker; persist an applied-range/cutoff receipt alongside the existing backup/marker, including zero-change results. A crash after the Room ledger commit but before marking applied must resume from the **same staged evidence and descriptor**, never from a new cloud read with a changed `through`, start or cutoff. An applied range is immutable; a different selection requires reversing first. Reversal restores originals and created IDs exactly as today **and reverses any pre-data transfer** (described below); subsequent fresh choices require a new confirmed acquisition. Keep Undo reachable for an already-applied re-file even if the endpoint becomes unavailable, subject to the existing local-account reset semantics. Ordinary Steam totals, combined credited playtime, XP and levels do not change when already-imported minutes are reclassified.

*Rejected:* re-running the apply against each newly selected range (would overwrite the originals needed for exact reversal); treating an empty-change application as un-applied (would make later evidence silently change an already-confirmed one-time operation); storing only the selected date in a transient ViewModel (crash recovery and display would disagree).

### Pre-data cutoff and conservative conversion of imported minutes

The **range start** means “how far back to acquire”; it is not proof of when Backlogium started. Ask the player to explicitly select and confirm a local date/time that bounds the end of their pre-Backlogium period; convert it to a frozen exclusive UTC cutoff and show the timezone/offset. Validate `effective start < cutoff <= through`; reject ambiguous/nonexistent DST local times rather than silently shifting the boundary. Do not infer a first-install timestamp from the earliest session (there may have been an earlier baseline but no recorded play) or from pruned diagnostic sync runs. A user who cannot identify a defensible cutoff can still re-date existing sessions without opting into the pre-data transfer. This cutoff is a user assertion and the UI must not describe it as a proven first sync.

Transfer is available **only if the independent Steam-history import was already opted into and has a positive frozen `backfillMinutes` balance for a Steam-owned game**. Snapshot that balance under the existing sync/derived-write locks at the commit point. Per game, enumerate confirmed, non-overlapping full-minute slots in staged presence intervals within `[effective start, cutoff)` (also not after `through`), applying the existing consumer coverage tolerance and rejecting unknown/tail/interior-gap spans. Do not reuse a slot that overlaps a session already in the ledger or a replacement session produced by this same operation; that session has already counted its Steam minutes even if its estimated timestamps are imperfect. If a candidate crosses local midnight, split it into dated rows so every minute is credited only to the row's start date; do not credit an unobserved portion. Convert at most `min(imported balance, eligible confirmed whole minutes)` and leave the rest imported/undated. Where the pool of safe minutes is larger than the budget, choose the **most recent** eligible slots before the confirmed cutoff, deterministically; this favours play nearest the asserted baseline but still cannot prove exactly which pre-install Steam minutes were counted. Disclose that distinction: presence locates plausible observed time, whereas the frozen Steam balance alone authorizes the quantity. The oldest user-selected date is available for evidence, not a promise that every game has imported minutes there.

Create ordinary *closed* History session rows for converted slots, marked as timing-informed Steam play (not family-shared recovered play), and subtract exactly their summed minutes from `Game.backfillMinutes` **in the same Room transaction**. The game detail's tracked/session aggregate rises by that amount, its imported offset falls by it, and `backfillMinutes + session minutes` and Steam's `playtimeForever` stay fixed; a silent derived-state recompute corrects historical daily quests and streaks without a new XP/level event. Compare game-specific before/after inputs in tests, not only the headline lifetime Steam total. The receipt reports minutes newly dated vs still imported per game and affected dates; History must render the dated rows through its existing session feed (including Load older), clearly indicating that their timing was reconstructed from cloud evidence rather than measured by an on-device session.

*Rejected:* deriving owned-game minutes from cloud duration without a Steam-counted budget (presence may include idling/unobserved spans and would invent XP); silently converting all imported history (some predates the poller); inferring the install cutoff from first stored session; displaying an undated imported offset as if it had exact historical sessions. Selecting most-recent eligible slots is a deterministic conservative attribution heuristic, not a proof of exactly which minutes Steam counted there.

### One journal for re-dating, transfer, and reversal

Extend the existing one-time re-file plan to include the immutable selected range/cutoff, original sessions, created IDs, and per-game imported-minute **deltas**; keep a Room operation journal alongside the staged evidence. Build the new rows and replacement plan from the completed stage, then commit owned-game offset reductions, session inserts/replacements, and the journal's apply-committed state atomically in Room before updating the DataStore applied receipt and silently recomputing daily/progression state. A retry after a process death consults the journal, never recalculates a different amount from a new Steam total or current presence. Reverse deletes only rows the operation created, restores only originals it modified, and **adds back the recorded per-game transfer deltas** rather than writing old absolute offsets, so unrelated later game updates survive. The reverse Room transaction advances its own journal state; a death between that transaction and the DataStore marker cleanup must not add offsets twice. Keep the recovery signal until all side effects and the marker settle. Disallow a new range while one is applied; if an earlier build applied an old-style re-file without a range receipt, retain its old exact undo path.

Guard the existing Steam-history import **Reset** in the use case as well as Settings: while a cloud re-file with a transfer is applied, it explains “Undo the cloud re-file first” and does not clear the imported balance. After reversal, the separate import reset works exactly as before and leaves ordinary tracked sessions untouched. An import that was never opted into yields no pre-data transfer; do not silently opt it in or change XP. Endpoint removal must not remove the applied local undo. Account reset must not resurrect transferred amounts under another Steam identity; the journal/receipt is account-bound.

*Rejected:* storing a pre-data transfer only as newly created sessions (would double-count against unchanged `backfillMinutes`); setting the offset to a recorded old absolute value on undo (could overwrite later legitimate updates); allowing Steam-history reset during an applied transfer (undo would restore imported credit despite the user's reset); using only an in-memory plan for cross-Store crash recovery.

## Risks / Trade-offs

- **Firestore cost for very dense history** → strict per-request/per-tap caps, no automatic continuation, transparent progress and worst-case estimate above. The fixed end makes total work finite for each confirmed job, but cannot promise a timeless whole-history ceiling.
- **Large local stage / Room migration** → persist incremental interval upserts rather than a DataStore set or giant in-memory list; test migration from the previous schema and bound per-batch memory. Full retained history still consumes local space proportional to relevant intervals; surface low-storage failures without applying.
- **First/last interval at a selected boundary may be uncertain** → one predecessor and frozen current when valid; clip eligibility and use existing coverage/complete-placement rejection instead of guessing.
- **Reader replacement, backup/restore and account reset can leave stale stage** → bind stage to durable identity/generation, clear on existing fences and reset, verify identity before every page/apply; never reverse a different account's ledger.
- **Current snapshot moves during paging** → freeze at confirmation and do not treat later current as historical evidence.
- **The confirmed cutoff is not a verifiable first-baseline timestamp** → make it a separate, explicit user assertion; show the exact instant and prevent automatic eligibility from first-session or diagnostics guesses.
- **Presence does not certify Steam-counted minutes within every observed slot** → cap conversion by the frozen imported balance and safe coverage, label dating as inferred, leave ambiguous/uncovered minutes imported, and permit exact reversal.
- **Import reset or later Steam changes collide with a transferred balance** → block reset until cloud undo, restore offset deltas rather than absolute snapshots, journal Room commits, and test crash paths in both directions.
- **Older endpoints do not support historical parameters** → deploy endpoint first, then app; historical lookup failure has a clear retry/compatibility message, with existing ordinary reads still functioning.

## Migration Plan

1. Ship the backward-compatible endpoint and document the request modes; retain bearer-before-Firestore and existing function instance limits.
2. Add Room staging/journal tables and migration plus an applied-range/cutoff receipt in settings storage; existing applied re-files keep their reversible backup and display “range not recorded by older version” rather than invent a date. Do not reset existing ordinary or ingest watermarks on upgrade. Existing imported balances and sessions stay untouched until explicit confirmation.
3. Ship Settings range/cutoff choice, import-reset guard and opt-in historical conversion alongside the existing re-file. Update `README.md`, `docs/architecture-map.md`, and `functions/README.md` to describe the already-implemented reader and the new historical contract accurately.
4. Rollback of the app leaves the new stage inert; earlier clients still send ordinary reads. A completed older-style re-file keeps its backup/undo path. Endpoint rollback disables only new historical operations; ordinary reads stay compatible.
