### Writer and lock/transaction map

- **Raw observation writes:** worker -> `PlaytimeObservationCommitter.commit` -> recovery-state read and `SessionDiffer` within caller `Room.withTransaction` -> `PlaytimeRecoveryCommitAdapter.commitPlanGraph` -> recovery DAO, `SessionActionWriter`/`SessionDao`, raw daily credit and finalization journal. The same transaction carries baseline/high-water, snapshots, authorized contribution, active placements/recipe, session and raw daily-credit changes; failures must roll all of them back.
- **Raw replacement writes:** `RecoveryPlacementReconcileUseCase.reconcileLocked/commitRawGraph` runs the delayed replacement path in a Room transaction and writes replacement/supersession revisions, recipe/allocations, session links, journal and raw daily deltas. It must not increase authorized quantity.
- **Materialization writes:** `UnknownTimeMaterializer.materialize` wraps recipe cursor/prefix materialization and daily-credit delta in a database transaction.
- **Restore writes:** `BackupMergeEngine.mergeRawWithLockHeld` calls `DatabaseTransactionScope`/Room transaction; `DaoRecoveryBackupStore.apply` writes account-scoped recovery state, observations, graph and journal along with games, sessions, daily progress, achievements, collections/hidden data and pending recompute. `merge` serializes with `SteamSyncCoordinator` and the derived-write coordinator; restore recomputation is deliberately outside the raw Room transaction.
- **Derived writes:** `RecoveryDerivedFinalizer` uses `DerivedStateWriteCoordinator.withLock`; both corrective and earned results persist via `RecoveryDerivedCompute` -> `GamificationUpdater`/versioned persistence, then mark journal stage. `BackupMergeEngine.recomputeAfterMerge` and worker tails use the same derived-state engine/serialization boundary. A `RecoveryPlacementReconcileUseCase` lazily constructs its own finalizer instance; workers inject a separate instance, so the mutex is per injected coordinator instance, not a single global object by construction.
- **Account/reset writers and fences:** active Steam identity is read from `PlayerProfileDao` and recovery DAO; `CredentialsProvider`, `EncryptedCredentialStore`, `AccountChangeMarkerStore`, `AccountChangeCoordinator/Gateway`, and profile/hidden/recovery DAO clear/update paths participate in account transition. Recovery DAO exposes `clearAll`/`clearForAccount`; restore admits identity-only-if-blank in `BackupMergeEngine`. These paths require stale worker/reset/restore tests; this map alone does not prove complete lifecycle isolation.
- **Observed lock boundaries:** process `SteamSyncCoordinator` mutex wraps worker phases, but code comments define it as an optimization; database baseline re-read is the quantity authority. Reader validation/promotion is held before and across Room (`reader state -> Room`). Targeted generation has a separate per-app mutex. Finalization's derived mutex protects the stages but is not held continuously across the workers' raw commit: `SteamSyncWorker` exits the sync lock after raw commit and reacquires for finalization; `PostPlaySyncWorker` likewise exits and reacquires. Startup pending-resumption runs before a new fetch, not continuously around a competing raw commit. The actual pending-finalization interleaving safety remains unproved (R2). Preserve account/sync -> reader-generation -> Room ordering when testing any repair; never move network fetch under the database transaction.

### Canonical quantity/date consumers

- All-time owned credited totals: `SessionRepository.trackedMinutesByGame` -> `PlaytimeReadProjector.creditedMinutesByGame`, with funded contribution shares plus only unlinked legacy session remainder. Used by Library/XP, collection/game displays and feed consumers (`LibraryViewModel`, `CollectionViewModel`, `GapPlanFeed`). `creditedMinutesByGameOnce` is the one-shot counterpart. Shared games remain on their existing session-only path.
- Dated canonical activity and totals: `activityBetween`, `datedAllocationsBetween`, `datedCreditedTotalsBetween`, `pendingDateUnknownQuantity`, `earliestCanonicalActivityDate`, and `datedRecoveryActivity` feed `HistoryViewModel` and `AnalyticsViewModel`/screens. Date keys for timed shares are frozen; recipes are window-bounded; pending date-unknown quantity is all-time only, not dated credit.
- Personal Pace/training: `closedTrainingTotalsBetween` and `unresolvedRecoveryWindows` (projected via `PlaytimeReadProjector.trainingTotalsBetween`, recovery/allocation estimate windows) feed pace calculations. Open sessions do not become closed-session training evidence; unresolved multi-day allocation is withheld according to the existing policy.
- Derived progression: `GamificationUpdater` consumes canonical activity for XP/level, quests and streaks; `ProgressEventDetector`, `ProgressMarksStore`, and `ProgressTransitionCoordinator` manage delivery/acknowledgement. Achievement refresh/rarity and collections consume their own existing paths. Recovery must not manufacture session counts, exact clocks, recency, or time-of-day evidence.

## 2.4 R3 input-boundary audit and disposition

- **Reproduction checkpoint:** at source HEAD `0ee8772035683aedccf10d1af07c9ed1ac774e63` (before the R3 validator edits), the expanded `BackupRecoveryValidatorTest` ran 33 cases with 6 failing boundary assertions. Full-file preflight accepted: observation high-water above `Int.MAX_VALUE`; a contribution endpoint above `Int.MAX_VALUE`; a contribution range beyond its same-epoch observation high-water; a contribution with no same-account/app observation; and recovery account fields inconsistent with the backup's root identity. The sixth candidate was a contribution epoch numerically greater than the selected observation epoch. Planner testing then showed that a legitimate merge of independent backup lineages can retain such a contribution while the timestamp-winning observation is from a lower epoch; when the contribution endpoint is covered by the retained max high-water, rejecting by epoch ordering alone would make the merged export invalid. That case is now a positive compatibility control, not a defect claim.
- **Representability repair:** the live `SessionDiffer` poll, prior baseline, and `Game.lastPlaytime` are `Int`-bounded. `BackupMergeEngine.syncGamesWithObservations` had silently coerced a larger `Long` high-water into `Int.MAX_VALUE`, leaving the persisted recovery state and detector pair unequal. No saved quantity is clamped. A real `BackupRepository.importBackup` test verifies the rejected over-range observation leaves seeded Room state unchanged.
- **Observation/contribution coherence:** every v3 contribution now requires an observation for its source account/app. A same-epoch contribution endpoint must not exceed its observation high-water. An older-epoch contribution remains valid beside a deliberately re-established newer epoch even if the newer high-water is lower. A different/newer epoch contribution from an independent merged backup lineage is permitted only when its endpoint is covered by the retained high-water. Tests cover missing observations, same-epoch overflow, uncovered alternate-epoch quantity, the `Int.MAX_VALUE` edge, and the legitimate lower-high-water older epoch. `RecoveryBackupMergePlannerTest.divergentEpochLineages_mergeToAValidBackupWhenRetainedHighWaterCoversBoth` confirms the actual segment planner's supported multi-epoch merge remains a valid v3 export under this rule.
